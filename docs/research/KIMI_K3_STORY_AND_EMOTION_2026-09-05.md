# Kimi K3、剧情驱动与情感写作：机制与验证方案

日期：2026-09-05。作者已认可 1177 字的局部编辑示范，并明确希望改用 Kimi K3。目标一是成熟网文应有的剧情吸引力，目标二是有积累、能打动人的情感表达。两者应共同设计。

## 核心判断

冲突是网文持续吸引读者的重要来源，但“发生冲突”本身不够。读者需要先在意人物想保住什么，再关心他如何跨过阻碍，以及付出后能否得到回应。危险越来越大却不改变选择，仍可能让人疲惫；平静的一次拒绝或一次交心，也能改变后续行动。

本轮采用的编辑框架是：**欲望与牵挂 → 行动 → 抵抗 → 代价 → 改变选择 → 回报或新的难题**。这是针对本项目的工作假设，不是已被验证的网文留存公式。不把争吵、打斗、情绪词或章末悬念的数量当质量指标。

原运行器主要回答“发生了什么、是否连续、是否收束”。这对成稿必要，却不足以回答“为何愿意继续看”和“为何在乎这两个人”。因此本轮把选择压力与关系变化放进计划，并在原文审稿里分别观察兴趣与情感。

## 剧情与感情怎样共用同一组事件

剧情链关注：主角想做什么，谁或什么使它变难，试过之后还能不能用原办法，代价由谁承担。

关系链关注：双方各自想要什么，如何理解对方的行为，试探或付出是否得到回应，之后愿意透露、请求或承担什么。关系变化要能影响下一次选择，而不只是旁白宣布更亲近。

以 U002 为例，可供作者选择的安排是：

| 事件 | 剧情作用 | 情感作用 |
|---|---|---|
| 王磊对追问产生戒备 | 凌默失去低风险获取信息的机会，需要改变接近方式 | 凌默体验好意未被接受，帮助别人不再是无代价的自我肯定 |
| 秦思妍发现卷子和伤手的问题 | 睡眠债与伤势真正影响高考生活，逼他分配时间 | 她的关心带着自己的职责、疑惑和边界，不是随叫随到的护理功能 |
| 凌默拒绝解释或掩饰 | 暂时保护秘密，同时失去一部分帮助 | 对方可以不信、失望或只帮自己能帮的部分，不必立即理解主角 |
| 救人后主动接受一项普通帮助 | 展示行动的现实后果，让下一阶段有新处境 | 关系可以只前进一步：愿意请求、愿意回应。仍然是普通同学，也能有情感分量 |

这些是结构例子，未加入正式小说。具体事件仍以作者简报为准，不要求每个单元都走同一顺序。

## “有感情的文笔”要落实到什么

1. **注意力有偏向。** 人物留意对方哪处变化，与他的经历和在意有关；不要让任何人都只看见“眼睛红了”。
2. **动作有两种含义。** 一句催交卷子，可以同时承载职责、担心和不愿显得过分关心；通过上下文让读者读到，不补一段解释。
3. **付出有分量但不强求惨烈。** 时间、自尊、一次袒露、放弃原本坚持的做法，都可以成为代价。
4. **对方有自主回应。** 可以接受、误解、拒绝、暂时搁置。配角有自己的需要与限度。
5. **小细节有积累与回响。** 同一个物件或一句话后来换了意义，才值得记忆。不能只复现物件名称来冒充伏笔兑现。
6. **内心描写保留必要部分。** 压缩重复解释，不是删除内心。那些改变读者对选择的理解、让外在行为显出矛盾的念头，应该保留。

感情线需要空间，但不设每章对白比例、好感分数或固定亲密升级。也不靠突然表白、误会拖延、反复受伤或强行牺牲制造感动。是否打动人只能由具体读稿验证。

## 1M 上下文、缓存与压缩的区别

Kimi 官方文档列出 `kimi-k3` 支持 1M tokens；输入与输出共享上下文预算。1M 不是 100 万汉字，也不是对全篇人物理解的质量承诺。[Kimi API 概览](https://www.kimi.ai/help/kimi-api/api-overview)

OpenAI Responses 提供自动压缩和独立 `/responses/compact`。返回的是包含不透明加密状态的上下文窗口，应按其协议继续送给 Responses，不能把它当通用文本笔记直接交给 Kimi。我们可以借鉴保留关键状态的思想，但不直接接入这份加密输出。[OpenAI Compaction](https://developers.openai.com/api/docs/guides/compaction)

Kimi 的上下文缓存用于复用输入计算、降低重复输入成本。它不负责挑选剧情重点，不会自动修复矛盾，也不把满窗口变成无限记忆。应把稳定材料放在稳定位置，并以供应商返回用量验证实际命中，而不承诺每次都命中。[Kimi Context Caching](https://platform.kimi.com/docs/guide/use-context-caching-feature-of-kimi-api)

对于不足 3 万字的当前单元，先保留此前工作稿全文，审稿看整单元。没有必要为了“用了压缩算法”而先丢掉小动作、对白和伏笔。真正需要压缩的通常是很长的旧正文、反复讨论记录、废弃候选和工具输出。

### 建议的显式记忆结构（尚未实现自动压缩）

| 层 | 保存内容 | 使用边界 |
|---|---|---|
| 作者规则 | 当前确认的设定、禁改项、关系允许到哪一步 | 独立保留，摘要不能覆盖 |
| 因果笔记 | 人物目标、已试办法及失败原因、资源变化、未兑现承诺 | 标出章节与证据，猜测不能升级为事实 |
| 关系笔记 | A 如何理解 B、B 实际做了什么、未说出口的冲突、尚未回应的付出 | 不用一个双方共享的好感分替代 |
| 情感原文锚点 | 关键互动的少量完整段落、具体措辞和动作 | 与摘要同时保留，必要时回读前后文 |
| 最近正文 | 最近若干章与当前单元此前工作稿全文 | 保留时间、动作与声音的连续性 |
| 未来计划 | 尚未发生的作者目标与候选路线 | 单独标识，不写进已发生记忆，不作为人物知识 |

例如，弱摘要是“秦思妍关心凌默，关系升温”。更有用的笔记是“她注意到他把前题答案抄进新题，先拉开沾血的卷子；他没有继续说没事，第一次借她的解题步骤。双方未谈灵异；证据指向具体两段”。关系含义可以写为编辑推断，并与原文事实分开。

自动压缩应在旧单元结束、作者确认或上下文预算确实承压时触发；候选笔记仅属于当前草稿分支。压缩前后检查仍能否回答：为何不能再用某办法、谁知道什么、哪次付出尚未回应。保留原文与哈希，发现丢失时回读。当前不新增向量库或复杂人物图，先验证这套文本笔记是否真正改善写作。

## 已实施的改动

- 本地默认接入 `kimi-k3`，规划与审稿继承同一提供商，实际调用失败不会退回 DeepSeek。密钥仅在 Git 忽略的本地 `.env`。
- K3 使用 `max_completion_tokens`，支持 `LLM_REASONING_EFFORT`；不发送 DeepSeek 的 thinking 开关或可调温度。K3 始终思考。high 的规划超时后，low、180 秒超时配置跑通整单元，本地默认据此切到 low；这是运行配置选择，不是质量优劣结论。[K3 参数说明](https://platform.kimi.com/docs/guide/kimi-k3-quickstart)
- 新客户端可调用官方 token 估算接口，为输入和预留输出共同检查预算；重试增大输出额度时再检查。超限明确拒绝，不截断原文。字符保护仍独立存在，长前情需明确提高 `--max-prompt-chars`。[Token 估算接口](https://platform.kimi.ai/docs/api/estimate)
- 简报加入读者体验与关系侧重点；计划保留每章选择压力、关系变化及单元关系发展。旧输入仍可读取，平静章不强制变化。
- 审稿增加读者兴趣和情感效果的原文观察，段落引用仍经过绑定校验。这些观察不直接决定接受或重写，不冒充读者实测。
- 旧 `continue_novel.py` / rewrite 所用客户端也优先读通用 LLM 配置，并处理 K3 请求参数；没有把旧 DeepSeek 凭证复制到新地址。

本轮没有实现自动记忆压缩、1M 满窗口质量测试、实际缓存命中优化或可靠的情感评分；不会把上述设计建议说成已完成能力。

## 哪些架构现在不值得继续加

新单元运行器未接入旧 `evaluator` 的冲突密度、情绪词和对白比例评分，也不依赖 `memory_rag` 或逐章 NovelState 提交。这些旧能力可用于文本分析和正式版本管理，但不应成为每次起草必经的流水线。冲突词变多不能证明人物的处境改变；关系共现或正面情绪增加也不能证明感情成立。

本阶段保留简短计划、连续全文、原文证据审稿、有限修订和隔离版本即可。不增加多代理投票、关系数值模拟和新的向量数据库。只有在实际读稿暴露出明确遗忘问题后，才增加可回读原文的笔记；只有盲读比较改善了具体段落，才让新增模块留在主流程中。

### 对 6327 字初稿的直接阅读判断

它尚未达到成熟网文成稿目标。第一章有清楚的异常引入，第二章王磊含着馒头哭的动作使被救者短暂显出主体感；秦思妍从追问到限定回复时间，也比单纯说“关心”具体。但是：

- **因果证据被笔记伪造。** C02P0020 写花卷被抢回并立即吃掉，C02P0030 却写“断食四小时”，再据此推导共享状态。两轮机器审稿都把这条错误因果当优点，证明引用绑定只保证来源存在，不保证解释正确。
- **结果被降低。** C02P0053 写异常声缩回体内，作者要求的“先保住再驱离”没有落实。v0 审稿明确写“未驱除”，仍判 complete=true；不能自行把未完成目标改成允许保留的长线。
- **观察重复挤占阅读。** 第一章先呈现异常、逐条记下，再逐条解释、抄写、回想；第二章又从方案清单讲起。作者要求观察记录，并不要求同一信息被多次重新讲述。
- **关系积累仍偏单一。** C01P0087 的借笔记与 C02P0081 的明确追问有可用进展；C02P0084 又送纱布与药膏，仍沿用照料受伤者的模式。物件重复可以有意义，但本稿尚未充分展开秦思妍自己的需要及凌默对它的回应。不能因“并排放着”就宣称已打动读者。

以上是对具体段落的编辑判断，不是读者盲测。新增两个事实失败用例，保存于 `experiments/unit_runner_v1/regression_cases.json`。审稿提示进一步要求沿“实际行动是否成功 → 可观察结果 → 推断能否成立”回查笔记，并逐项核对作者结局，不能自行降低目标。用同一份 v0 做定向回放；这类针对已知失败的修补不能当成泛化能力证明。

**回放结果仍失败。** `audit-evidence-v3/review.json` 仍把断食视为已执行，并将阴物缩回判为符合结局。它指出了送药互动重复，但修法用扣留药膏交换解释，也不能直接采用为成熟人物互动。增加审查提示没有修复已知核心错误；目前不能声称可靠的因果审稿已经实现。下一项值得验证的是把关键推断单独拿出来核验行动、结果和反证，减少全文评价中多目标争夺注意力；需要与现有整稿审阅做相同输入比较，再决定是否增加这个步骤。

## 研究支持与适用范围

DOC 将创意规划与正文控制分开，在其故事任务中改善连贯性与提纲遵循。它支持认真设计因果再生成正文，不证明我们的中文网文一定好看，也不要求照搬其细纲粒度。[DOC](https://arxiv.org/abs/2212.10077)

StoryWriter 使用事件规划与按当前事件组织历史信息。它说明长故事的记忆与事件组织值得独立设计；本项目不据此增加多个并行代理。[StoryWriter](https://arxiv.org/abs/2506.16445)

IPOCL 将人物意图纳入叙事规划，关注行动能否被目标解释。这支持“人物为何这样选择”比“事件是否出现”更接近我们的检查目标。[Narrative Planning](https://arxiv.org/abs/1401.3841)

STORIUM 明确讨论长篇创作自动评价的不可靠，并提供作者参与的故事生成数据和评价方式。因此这里保留作者对具体候选的判断，不把同一模型自评当成审美真值。[STORIUM](https://arxiv.org/abs/2010.01717)

## 下一步如何判断是否有效

先固定作者方案、篇幅、前情和模型配置。至少比较“原简短规划”与“选择压力及关系发展规划”，再比较是否增加显式笔记；不要同时换模型、换剧情、换篇幅后宣称某个算法胜出。

通读时记录三个实际问题：哪里想跳读；哪里不相信人物会这样做；哪次互动改变了对人物或关系的感受。再记录作者真正要改的段落及原因。机器做事实与证据初筛，作者比较匿名候选。一次案例只给局部结论；稳定成稿需要多个单元和不同关系类型重复验证。

本轮 K3 样本是迁移与机制试写，同时改变模型和提示，并使用作者认可的示范作风格参照。它不是控制变量实验，不用于证明 K3 优于其他模型。
