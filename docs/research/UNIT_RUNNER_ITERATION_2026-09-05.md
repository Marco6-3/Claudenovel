# 单元写作流程迭代与实测记录

日期：2026-09-05。承接同日 `UNIT_WRITING_REVIEW_2026-09-05.md` 的只读复审；本文件记录后续已实施的修改和新 API 实验，避免把两个阶段混为一谈。

## 当前判断

已经补上“作者方案 → 完整单元草稿 → 整稿审阅 → 有限修订 → 交作者”的独立入口。它能在不逐章确认的情况下保存完整候选，并把正文硬上限设为 29999 个非空白字符。

写作能力仍应评为“能自主起草、需要编辑通读”，不能评为“稳定交付可直接采用的小说”。实际运行同时暴露了模型漏检、事实问题严重程度误判、局部写作提前收尾、引文抄写失败等问题。已经修复若干工程与流程问题，但引用有效、机器通过、正文写完都不代表因果自洽或文学质量合格。

## 实施的架构

新入口是 `agent_writer_cli.py unit-run`，核心位于 `agent_writer/unit_runner.py`。

- 作者可直接给 Markdown 简报，或使用带明确结局、作者锁和篇幅预算的 JSON。
- 计划只保留主要发展、起始状态、结果变化及必要的结局铺垫。短单元一次写完，较长单元用连续长段起草，避免强制逐场拼接。
- 初稿写作保留此前已写的单元全文；修订写作保留前章与目标原章，隔离后章正文，避免未来经历倒灌。审稿保留完整单元。前情由作者明确选择，超限报错，不静默丢弃约束。
- 审稿不看计划的自我解释，从正文重建目标状态，引用实际段落编号。程序负责提取原文，避免模型抄错人名或代词。
- 事实、因果、作者约束及结局问题进入修订；minor 文字意见仅供参考。最多两轮，跨章联动，机器待修问题数未下降便保留原稿并停止追改。
- 普通创作留白自行补全并披露；规划阶段的方向问题必须附输入中两条不同原话。只能验证引文存在，仍不能机械证明真实矛盾。
- 输入、提示词、原始响应、用量、草稿和版本均留痕。中断可恢复，旧完整稿可通过 `--from-run` 复用后重新审阅。

保留 API 客户端、文件存储和原有正式验收能力。新写作链不依赖情感词典打分、词面“语义兑现”、每章爽点配额、证据图检索或逐章正式状态更新。那些模块仍可服务分析或旧项目，因此本轮没有直接删除；不再把它们堆到整单元生成的必经路径。

额外修复旧 `unit_completion.py` 的引文绑定漏洞：引文现在必须属于所引用 ID 的段落。对 Windows 同步目录的短暂共享冲突增加有限原子替换重试，不删除原目标文件。

## 阅读判断

现实短篇的较好样本可以自然组织道歉、共同找书与不完全和解，没有必要强加章末钩子。其主要欠缺是细小动作交接和人物反应的精确性。

U002 原稿的食堂异常、伤势和学生生活可读，局部感官描写有效。但“观察—记笔记—总结规则”反复出现，常把人物判断写成任务摘要。第三章耗尽真气、第四章又有真气，未署名短信却记下发信者姓名，都是需要修的具体事实问题。高潮“短暂隔开再驱离”也需要在行动与效果上成立，而不能只靠事后说明。

这里的写作评价是通读后的编辑判断，不给没有校准意义的百分制分数。下一阶段最需要的是作者认可的目标稿与修改负担评价，而非再增加一套自动评分字段。

## 验证与边界

相关回归测试 78 项通过，覆盖恢复、预算、作者边界、证据绑定、跨章修订、保留较好版本、规划问题处理、作者反馈修订中断后的恢复与继承，以及保留正文的标题规范化。编译检查和本轮已跟踪改动的 diff 空白检查通过。单元测试不代表模型写作质量。

代码在 `feat/unit-draft-runner`，尚未提交或推送。用户既有修改及旧 Harness 工作区保留，实验不更新正式正文、accepted 或 NovelState。当前只实测约 2.4 千至 1.3 万字，不宣称已验证接近 3 万字时同样稳定；输入总字符保护也不是精确 token 预算。

后续优先做固定作者方案下的成稿对比，统计作者需要修改哪些段落、是否破坏关键选择及为何弃稿。不要仅凭机器自评继续扩建架构。

## 后续运行与作者反馈

- `library-v7-default`：3 次调用完成 2443 字，普通细节不再阻断。机器无问题，但人工通读发现林禾突然知道陈屿在写论文（正文第 137 行，前文没有该信息来源）；三年前失书的目击者恰好坐在旁边，并凭模糊校服信息迅速锁定人选，线索过巧。这是模型漏检与叙事便利的反例。
- `u002-v5-repair`：复用万字稿，5 次调用完成三章局部修订及复审，采用 v1，11337 字，状态为 `needs_author_review`。补了真气恢复与分配，避免直接知道未署名发信者姓名；但新的审阅又指出知情范围、短信铺垫等问题。不能宣称自动修订已消除所有问题。
- 作者随后明确选择“压缩笔记与解释，增加互动和行动”。已增加 `--revision-note`，把这项要求作为可追溯的作者反馈，开展新候选修订；原稿保留，后续结果不与前轮机器缺陷修复混称。
- `u002-v6-action`：全角色开启思考的作者反馈改稿。首章先耗尽 8000 输出 token，再以 16000 重试，两次响应总耗时约 417 秒、报告 52096 token；返回正文仅因开头 Markdown 标题被旧校验拒绝。已停止本次自建进程，保存响应与中止原因，第二次逻辑调用的在途用量未知。修复为标题规范化，并提高思考模式初始输出额度；没有把失败抹掉或当作成功。后续改用普通 Writer、思考 Critic 完成反馈改稿，以检验可用性，不据此推断模型普遍优劣。
- `u002-v7-action`：普通改稿模式把后章高潮与收尾搬到第一章，人工发现后停止。改为显式标出唯一目标原章。
- `u002-v8-action`：目标正确，但第一章逐字不变，作者反馈未落实，停止后调整修改指令的位置。
- `u002-v9-action`：开始实际改写，却在第二章回忆第三章才发生的旧教学楼失败，人工发现后停止。根因之一是修订 Writer 可以读到后章全文。最终调整为只给此前工作稿和目标原章；Critic 保持全稿审查。这也修正了本轮最初“改章也尽量全量给全文”的设想。

以上人为停止均只针对本任务创建的进程；保留原始响应和中止原因。在途未返回的 API 用量未知。反复失败说明提示和上下文安排仍有明显影响，不能把新入口称为成熟产品。

### 最后一次完整运行

`u002-v10-action` 完成 5 章作者反馈改稿、整稿审阅、4 章联动修订和复审，共 11 次逻辑调用，选中 v1，正文 12928 个非空白字符，上限 14999。最终状态为 `needs_author_review`。本次供应商报告输入 176676、输出 44468、合计 221144 token。

互动确实增加，但没有稳定达到“压缩解释、用行动推进”的标准：部分记录只是换成简写，第二章显著扩写；赵灵瑶的提前告知被改成提前警告，依然影响主角选择。末轮 Critic 甚至建议补写主角如何忽略这条警告，而不是移除违背原定过程的前置介入。说明审稿建议本身也会偏离作者方案，不能只靠待修问题计数选稿来确保质量。

这是失败与局部改善并存的完整候选，不作为建议作者直接采用的成稿。需要区别“完成流程”与“实现写作质量目标”。

本轮共核验两个本地运行根目录的 15 个运行、529 个记录产物，哈希全部一致，无仍在运行的任务。这 15 个运行已返回用量合计 1074207 token；不含另行审稿探针，也不含被取消或超时但未返回的潜在消耗。它是开发阶段累计量，不是一次写小说的成本，不应拿来推算稳定生产费用。机器可读汇总在 `.local_projects/unit-validation/run_summary.json`。

## 需要作者校准的标准

作者已经选择增加互动与行动，下一步应拿具体文字校准，而不是再次询问同一个抽象偏好。本次审阅助手另写了 `.local_projects/unit-validation/U002_编辑示范_观察转行动.md`，只覆盖首次食堂异常和普通同学关心的局部段落。它通过王磊的反应改变凌默的询问与阻拦，通过卷子与伤手落实秦思妍的关心，保留首次必要记录。

这份示范不是 unit-run 的模型输出，不计入自动生成效果，也未合入正式小说。可由作者判断人物声音与叙述密度是否接近目标，再作为后续固定对照。当前证据不支持继续增加无校准的文学分数、逐场硬配额或自动正式验收。
