# 单元剧写作能力与架构复审

日期：2026-09-05。目标：作者提供单元剧方案，系统续写完整单元，正文严格小于 3 万字，完成后交作者审核。

## 结论

当前仓库能辅助生成章节草稿，但尚未证明能稳定交付完整、好读、因果自洽的单元剧。主要问题是生产流程围绕逐章验收设计、检查器偏向合同条目兑现、写作实测不足。建议保留基础设施，另建轻量的整单元草稿流程；不直接沿用全部旧架构，也不全盘重写。

“能写完”和“作者愿意采用”必须分别验收。测试通过、字数达标、审稿 JSON 合法都不等于文学质量达标。

## P0：目前流程不符合整单元自主起草

main 的 `pipeline.py:796` 要求逐章明确 approve；`rolling_arc.py:410` 激活下一章，状态更新后又要求重规划。`unit_completion.py:108` 则在所有章节 accepted 且状态同步后才允许整单元终评。

这使得“先写完整个单元，再由作者统一读稿”缺乏独立的生产入口。不要用自动 `approve=True` 绕过；应该增加隔离的工作稿状态，允许工作稿相互承接，最终确认才更新正式正文。

Harness 的 `generate_structured_draft` 也仍是单章入口。其三章比较脚本确实会把候选冻结到隔离实验目录供后章读取（`run_u002_comparison.py:764`），说明技术上已有部分基础，但不是通用单元运行器。这里的实验 accepted 不等于正式小说 accepted。

## P1：具体问题及影响

### 1. 词面检查冒充剧情语义检查

`agent_writer/quality_gate.py:66` 的 `_contains` 基于包含与字符清洗；所谓 `_semantic_contains` 只有染血校牌、校牌背面名字的特例。兑现事件、禁改项、人物红线都调用这一机制。

本次直接调用复现：

- `He did not find the key.` 对 `find the key` 返回 True：否定事件被当作发生。
- `He located the key.` 对 `find the key` 返回 False：同义兑现被漏检。

这是最小字符串反例，不是模型质量实验。实现同样无法普遍区分主体、时间、否定、猜测和已完成行为。人物禁行为在整篇文本中匹配，也没有可靠绑定行为主体。

建议删除校牌专用逻辑；关键词只做线索提示。重要作者约束由基于原文的语义检查提出明确问题，证据不足则保留不确定。编码、截断、字数、文件完整性才由确定性检查硬判。

### 2. 存在与具体旧故事绑定的阻断条件

`rolling_arc.py:134` 附近把“新的微信号”直接判为明显错词；这是特定案例修补，不是跨小说规则。合法的现代故事也可能真实出现这个词。

`agent_writer/rules/chapter_commercial_function.json` 把每章收益、爽点后的新问题、最后三到五段尾钩作为通用规则；`pipeline.py:341` 还要求最后三到五段落到指定结尾。这会把过渡章、日常章、余韵型结尾压成相似结构。应改成作者可选偏好。

### 3. 字数约束不一致，缺少提前收束能力

main 的 `models.py:526`、单元分支模型将上限限定为 20000；`rolling_arc.py:514` 到提交阶段按 `len(text)` 阻断超限。Harness 则支持最多 30000 非空白字符（`writing_harness.py:1128`），但等于 30000 仍会通过，不符合严格“小于”。

更深的问题是余额不等于收束方案。模型可以在前半段花掉大量篇幅，再因末章超限被拒。新流程应统一计数口径，记录剩余关键事件，给高潮和余波留软预算；发现余量不够时压缩未写内容或定向修订工作稿，不能硬截正文。建议默认正文非空白字符含标点、数字和字母，章节标题不计，硬上限 29999；这是建议口径，并非中文出版字数的唯一标准。

### 4. 上下文裁剪可能丢失关键事实

main 的 `novel_state.py:500` 先放最近章节，再放检索证据，再放状态。作者锁没有独占保留区，也受末尾预算淘汰影响。第一篇前文即使大于 max_chars 也可放入；max_chars 不是完整提示词 token 上限。

Harness 的 `writing_harness.py:427` 只取最近一章，将其正文压成最后 4000 字，加状态与少量远端证据。它能减少提示词膨胀，但对于不足 3 万字的当前单元，过早丢掉正文会增加资源、动作与伏笔细节丢失风险。

建议当前单元在实际 token 预算允许时优先保留完整工作稿；作者硬约束先预留，再加入历史摘要和相关旧章。超出上下文时按明确优先级缩减，不能静默丢作者硬约束。全书很长时仍需要按需检索，不能因单元短就认为整个前情也短。

### 5. 完成度与证据校验存在语义空洞

`unit_completion.py:186` 验证引用 ID 存在、引文存在于整篇证据拼接文本，却不验证引文属于所引用 ID。

本次复现：P1 为 `He slept.`，P2 为 `The door opened.`；引用 P1、引文用 P2 的句子，仍可通过并返回 met。应绑定引文与引用段落；绑定正确后仍不能替代“证据是否真正支持判断”的语义审核。

`rolling_arc.py:535` 的 completed 只代表所有 beat 已 accepted；并非整单元文学闭合或完成评分通过。建议拆成“生成结束”“待审”“终评通过”“作者采用”等不同状态。

## 实际写作能力判断

证据目录：Harness 工作区 `experiments/writing_harness_v2/runs/u002_20260823_phase_relaxed_v8/structured_project/`。

优点：第三章从进食异常、重叠咀嚼声到停止进食仍有声音，具备递进；教室和食堂的感官信息具体；秦思妍通过递错题集、关心手伤进入故事，比只复述人设自然。说明基础模型可以写出可读的局部段落。

主要缺陷：

1. 第四章 `drafts/chapter_0004_draft.md:103` 明确写“共享状态确认。杀伤性手段不可行”，159 行又强调不能再用符、输真气。第五章却在短暂阻隔后念驱邪咒第一个音节，成功脱险，之后由赵灵瑶说明先挡一下才救了人。文本没有充分建立“阻隔如何改变共享伤害”的机制及主角为何作此选择。这个动作可以写成冒险，但需要把判断、风险与实际效果接起来。目前关键解法主要靠事后说明成立。
2. 第五章第 3 行用“他不知道自己为什么要去食堂”承接第四章的无能为力，削弱了关键救人选择的主动性。
3. 第四章符紙使用过程不清：到第五张停下，垃圾桶四张，宣称只剩两张，接着跳到第六、七张；第五张去向欠交代。它未必构成世界设定矛盾，但显示细节账目没有被可靠核对。
4. 观察—记录—写结论反复出现，第四章末尾甚至使用接近任务摘要的笔记句。记录本可以是人物特征，但此样本频率使叙事呈现检查清单感。这是编辑判断，不是机械违规。
5. 第五章审稿 `reviews/chapter_0005_audit_initial.json` 给出 accept，并称“事件因果链紧凑”；`chapter_0005_structured_run.json` 为 machine_passed_initial。说明它善于确认目标条目出现，却仍会漏掉连接条目的因果问题。

该样本不支持宣称“已具备稳定成稿能力”，也不能证明某模型天生不行。提示词、上下文、合同本身及模型能力的贡献需要对照实验拆开。

## 哪些值得保留，哪些应退出默认路径

| 设计 | 建议 | 原因 |
|---|---|---|
| API 调用、超时重试、截断识别、原始结果留存 | 保留 | 必需工程基础，客户端已有 finish_reason 检查，不能误判为缺失 |
| UTF-8、哈希、原子保存、作者终稿 diff | 保留 | 保护用户作品并支持恢复 |
| 作者简报、禁改项、事实来源 | 保留并压缩 | 防越权，减少重复合同表述 |
| 正式正文与工作稿隔离 | 强化 | 支持全单元自动起草而不自动成为 canon |
| NovelState、StateDelta | 简化使用 | 保留跨单元事实；单元内部轻量账本须可回到正文校对 |
| 每章必做重规划 | 改成按需 | 偏离结局、事实改变或余额不足时才重规划 |
| 多层合同、逐场配额、每章大量 rubric | 减少 | 编排成本高，容易造成逐项演示和模板节奏 |
| Best-of-N、Branch-first | 可选 | 作者只给种子时可探索，完整单元方案不应默认再选多条路线 |
| 双顺序 Judge | 留作实验协议 | 可提示位置偏差，无法证明判断正确；不必每章默认执行 |
| 图检索、API rerank、向量召回 | 长前情按需启用 | main 默认其实为 state_only、rerank=False，不能声称图检索正在拖累默认路径 |
| 词典情绪、冲突词密度、TTR 合成文笔分 | 退出写作选优 | 可做描述统计，不能作为情节/文笔质量真值；当前主要在分析侧 |
| 本地 NLI 训练与大量银标制作 | 归档研究，不作前置 | 窄事实任务和银标吻合度不能证明写作提升 |
| webnovel-writer 快照、旧实验 | 单独归档 | 非默认调用不等于运行瓶颈；保留证据，避免多个入口造成混淆 |

这里的“退出”是架构建议，不是本次删除操作。现有文档已将训练任务收缩到 API 事实核验，不应把历史研究全算成当前实时开销。

## 建议的新流程

```text
作者单元简报 + 正式前情
  → 检查少量硬约束是否相互冲突
  → 简短因果路线与收束位置
  → 在隔离工作稿中按章连续写作
  → 更新临时事实账本与剩余篇幅
  → 必要时调整后续路线
  → 通读整个单元，检查因果、人物、兑现和重复
  → 有限次数的定向修订
  → 完整单元稿 + 简短待决问题
  → 作者采用后更新正式正文与跨单元状态
```

作者只需提供起点、核心冲突、希望发生的关键事件或结局、不能改的事、篇幅上限；已有正文和风格样例可复用。允许作者只给种子，由系统补足路线，但要标明系统补全内容。

内部可分为五个职责：输入上下文、单元运行控制、写作、整稿审阅修订、保存恢复。不需要五个自治 Agent，也不需要每项独立服务。优先复用当前存储和客户端。

临时账本只记会影响后文的事实：谁在哪里、谁知道什么、伤势/资源、已兑现/未兑现事件。事实标注来源段落，计划与人物猜测分开；账本不可压过实际正文。

运行控制应持久化阶段、每章版本、源正文哈希和字数。失败重启只重跑未完成步骤；修订前章后使受影响的摘要和后续审查失效。硬上限始终针对最终拼接正文检查。预算应给收束预留软空间，比例通过实验调整，不是新的固定文学规则。

关键是增加整单元的因果审阅：当主角发现 A 会伤人，后来仍用 A，必须在正文中找到新的条件、判断或明确的冒险动机，不能因“高潮目标出现”就通过。审稿者可以看到简报和全文，但不要把上一位审稿者的赞扬作为输入锚点。

## 怎样验证新架构确实更好

先做一个完整单元的端到端能力验证，再做至少六个不同单元的探索性对照。覆盖调查/行动、人物关系、日常过渡等差异，不把悬疑规则强套所有题材。

- A：相同模型、前情、作者方案，直接按章续写并带上已有工作稿。
- B：现有 Harness。
- C：轻量单元流程，加整稿审阅和有限修订。

同一输入、模型配置和总调用预算；记录实际消耗、重试及失败。所有分配的运行都计入，不只保留成功稿。样本少时只作方向性结论；有预算再增加重复运行估计随机性。

分别比较：是否写完且小于上限、作者锁是否遵守、高潮是否靠已建立条件成立、人物选择是否可信、重复与解释负担、作者盲选偏好、需要修补多少剧情和耗时。字面修改率只能辅助，不能等价于可用性。六个单元仍不够证明普遍优越。

暂不需要再训练分类器或增加候选 Agent。先确定直接写作基线究竟输在哪里，只保留能在整单元成稿上展示净收益的组件。
